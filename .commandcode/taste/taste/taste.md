- Answers a request it will not do with a two-part refusal: the rule quoted verbatim from the file that states it, then — explicitly as the more interesting half — the substantive engineering reason the same request is wrong here on its own merits (the credit that expires mid-quarter is the wrong substrate for user data; the database isn't even on the critical path, since the local-first path runs with no backend configured). Rule-as-shield alone reads as obedience, so support the no with facts already in the repo, size the blast radius in the units that exist (files touched, schema assertions pinned, tables with RLS), and close by naming which of the user's underlying goals *is* achievable with a concrete mechanism already built, plus a recommendation — then ask which goal was meant instead of leaving it as a flat refusal. Confidence: 0.7

- Works in shared repos where several agents commit concurrently, and stands up explicit collab machinery for it (lane/surface ownership files, a pre-commit guard that rejects out-of-scope or hot files). Expects an agent to stay inside its claimed file scope, name the owner in any claim line so tooling can recognise it, file cross-lane follow-ups in the shared board instead of editing another lane's files, and commit by hunk rather than by path: when another lane's uncommitted work lives in a file you also need, `git commit --only <path>` takes the whole working-tree file and carries their lines, so stage a hunk-scoped diff (`git diff -- <file> | git apply --cached`) and commit with no pathspec — then read back HEAD to confirm nothing else rode along. Never a blanket `git add -A`. Stash (or `--keep-index` around a path) whatever of other lanes' work is sitting in the index or working tree, rebase past it, and pop it back untouched rather than committing it; when a conflict is only in the coordination file itself, taking upstream's version is the right resolution, and confirming a rebase is unblocked means re-testing it on a clean tree, not reading the neighbours' dirty-file error. When the file is so contended that even the hunk-scoped patch sweeps a neighbour's lines in, drop to the blob: read HEAD at the moment you build it, compose it plus *only* your own lines, assert the replacement is present in the composed text, `git hash-object -w` it, `git update-index --cacheinfo 100644,<sha>,<path>`, and count the staged `+/-` lines against what you expect. Commit that with **no pathspec** — passing `--only`/`-- <path>` alongside a cacheinfo blob makes git re-stage the path from the working tree and silently discard what you just cached, so the commit reports success while changing nothing; a clean worktree is exactly the setup where that trap fires. When you made the contended edit with the normal edit tool first, take your own line back out of the blob composition by a unique marker — assert exactly one line matched — rather than committing the file as edited.
