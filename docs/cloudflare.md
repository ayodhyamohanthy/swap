Verify token permissions, exact current and destination account IDs, the owner's confirmation of the target, credit balance and expiry. Inspect relevant GitHub deployment settings and secret names, not values. Record stable IDs and source paths in a reviewed manifest. If Swap already resides in the intended account, prefer a no-op to an unnecessary move. The token must not grant broad DNS or account administration without a separately approved need.

Before any future write, require an account-ID and resource-ID allowlist guard in the deploy process. The guard must check the authenticated account, repository, environment, config path, exact Worker name and binding IDs against a reviewed manifest, and reject missing or mismatched IDs, wildcard targets, unknown resources and references to other projects. For newly created names, enforce swap-. Legacy seatswap resources may appear only as explicitly approved source/read or rollback targets. A scoped token alone may not enforce isolation between every Worker in a shared account; exact ID/name allowlists and protected production approval are also required. Any account-wide list access must remain read-only and must never become a bulk mutation loop.

The next gate is a recoverable baseline, not just an archive command. Capture current deployment version, built static assets, binding/route configuration and relevant DNS records. Verify a fresh Supabase dump, required auth/storage exports and the R2 object inventory, then restore into isolated staging and check row counts and application behavior. Protect all exports as sensitive data. Preserve source copies and the existing backup schedule. Any source-to-target bucket copy must have an approved object allowlist, checksums, counts, version/metadata handling and retention checks; do not delete the source. The nightly dump workflow must keep working throughout and must never be temporarily pointed at another project's bucket.

Only after those gates should a separate execution change add a scoped target configuration and a reproducible, pinned deployment tool. Run typecheck, full tests, build/verify-dist and collab-check. Run a local deployment dry run and inspect the exact artifact, proposed bindings and route diff with no remote writes. Check that client assets contain no server credentials. A dry run does not verify account ownership, grant permission to provision resources or guarantee a live deployment. Implement and test the deployment guard first; this draft did not modify tooling.

With approval for staging resource creation, deploy only swap-* staging resources in the verified destination account. Keep production routes and sources untouched. Exercise auth with staging redirects, RLS separation, server functions, payment test-mode webhooks including signature rejection and replay tests, cron idempotency, queue retry/dead-letter behavior if queues are actually needed, backup/restore, offline service-worker behavior and deep links. Test rejected cross-project and cross-environment targets. A functional server runtime and its routing must be designed and tested explicitly; switching accounts alone cannot close the static-runtime gap.

Production cutover needs a separate owner approval of exact account IDs, resource list, billing terms, backup evidence, staging results, maintenance window, expected interruption and rollback triggers. That approval must cover DNS or route writes and production secrets if required. No nameserver transfer is implied by this plan.
