## Defect 2 — `locked_berths` showed each party their own berth. Committed `880f571`.

**What was wrong.** Each party to a locked swap saw only their OWN berth, so rule 13's
post-payment reveal did nothing. Executed, before: A saw `{41}`, B saw `{52}`, a
stranger saw `{}`. After: A `{41,52}`, B `{41,52}`, stranger `{}`.

**Why it survived every test:** a stranger saw nothing throughout, so this was a dead
feature, not a leak. Privacy held. Nothing that checks for leaks can notice a reveal
that reveals nothing.

**The cause is a property of the mechanism, not a typo.** `security_invoker = true`
means "read the base tables as the CALLER". Part 7 drops `passengers_match_read` and
leaves `passengers_owner`, so the INNER JOIN on `passengers` lost the other side before
`berth_no` was projected. There is no `security_definer` view option to turn off.
**Only a FUNCTION can raise its own rights; a view cannot.**

**The fix:** `get_locked_berths()`, `SECURITY DEFINER STABLE SET search_path = public`,
checking party membership itself with `is_request_party(r.id, auth.uid())` and
projecting only `coach` + `berth_no`. `locked_berths` stays as a thin
`security_invoker` wrapper, so name, columns and grant are unchanged and no caller
moves. Re-adding a broad `passengers` read policy was the tempting fix and is the wrong
one — it hands every signed-in user every passenger row to make one screen work.

**Both copies, always.** #2–#4 ADDED objects; #5–#7 MODIFY objects init already
defines. So the fix lives in the baseline mirror AND a forward migration, pinned
byte-identical by an anti-drift test — because `chat-safety-parity.test.ts` reads the
BASELINE, and a migration-only fix would leave the tested copy broken.

**Guards:** 5 new tests, mutation-checked **12/12 caught, 0 survived.**

**Named, not fixed:** `locked_berths` has ZERO application readers. `revealedBerths()`
(`app/src/lib/requests.ts:783`) reads device `localStorage`. The view is the intended
server-side path that was broken before anything called it — same class as the profile
gate fixed on 2026-10-06.

## Defect 3 — the DB chat guard could not see evasion. Uncommitted at time of writing.

**What was wrong.** The trigger matched RAW text only. `s-e-l-l it to me` and
`call nine eight 200 12345` were flagged on the sender's device and stored
`flagged_risky = false`. `chat-sync.ts` trusts the ROW, so the receiver's screen never
warned. The warning reached nobody who mattered — the whole reason the DB copy exists.

**Measured, not read — and by direction.** `chat-parity-differential.mjs` runs the REAL
TS module (imported, not a retyped regex) and the REAL trigger under PostgreSQL 18.3
over one corpus. `TS=true/SQL=false` is a hole; `TS=false/SQL=true` merely hides
ordinary chat. Counting disagreements ranks those the same; they are not the same.

| tree | result |
| --- | --- |
| before migration #5 | 8 dangerous, 1 over-flag |
| after migration #5 | 3 dangerous, 1 over-flag |
| **after migration #7** | **51 cases, 51 agree, 0 dangerous, 0 over-flag** |
| pre-fix baseline (negative control) | 10 dangerous, 1 over-flag |

The negative control needs the OLD part: `git show HEAD:app/supabase/schema.part7.sql`.
Running against the already-fixed tree "passes" vacuously — that mistake was made and
caught in the previous session, so it is worth repeating.

**The repo's own excuse was wrong twice over.** `chat-safety-parity.test.ts`'s header
said it could not verify regex *shapes* because of "Postgres `\y` vs JS `\b`, and no
lookahead in Postgres". PostgreSQL 18.3 has lookahead AND lookbehind (proved with 10
paired controls), so the TS shapes port verbatim — and the shapes were exactly where the
defects lived. Header corrected.

**Three design points worth keeping:**
- **Sentinel** — `'[' || NEW.text || ']'` makes start/end of string behave like an
  ordinary non-letter, so the lookbehind/lookahead stay fixed width.
- **Boundary gate** — `(?<=[^A-Za-z][A-Za-z])…(?=[A-Za-z][^A-Za-z])` is what stops
  `Meet me near` collapsing to `Meetmenear`.
- **Pure-run rule** (docs/09) — stops a train number plus a berth becoming a phantom
  phone number.

**A reversal, recorded rather than quietly overwritten.** The migration-#5 entry called
the UPI over-flag "the safe direction and the stated requirement" and left it. Right
about the requirement ("DB at least as strict as TS") — but equal satisfies it, and the
*goal* is parity, because divergence is the defect class. `{2,}` is the reviewed spec, a
1-character local part is not a payable UPI id, and an over-flag teaches users to ignore
warnings. So the UPI shape came down to `[a-z0-9._-]{2,}@[a-z]{2,}` deliberately.

**Two holes in my OWN guards, found by review and not by a failing test.** The test
file's JS re-implementations *reproduce* the sentinel and the pure-run rule, so dropping
either from the SQL would leave every behavioural test green. Both are now asserted
against the shipped TRIGGER text directly. And the collapse test asserts EXACT output
(`squish('s-e-l-l') === 'sell'`, `squish('Meet me near') === 'Meet me near'`) rather
than keyword absence — a keyword-absence check would not notice the naive collapse,
because those sentences contain no money word either way.

**Guards:** mutation-checked **10/10 caught, 0 survived, 0 skipped.** The 10 mutations:
drop the squish test; drop the digit test; naive collapse without the boundary gate;
drop the sentinel; drop the pure-run guard; drop the leet decode; drop one digit word;
revert the UPI shape; drift the migration; move the migration out of last place.

**Named, not fixed:** `HINGLISH_WORDS`/`HINDI_WORDS` are still matched against raw text
in BOTH copies, so a spaced `b h e j` is caught by neither.
