## The suite would not run, and it is not this repo's fault

Three full attempts, all incomplete — `1 failed | 37 passed (38)`,
`2 failed | 51 passed (53)`, then `38 passed (38)` with `exit=1`. **Not one
assertion failed in any of them.** Every failure was `[vitest-pool]: Failed to
start forks worker … Timeout waiting for worker to respond`.

The cause is external. `pgrep -lf node` showed **another project's agents**
(`Documents/GitHub/skipwaitmanus`) running `pnpm vitest run --maxWorkers=1` and
`pnpm quality:gate && pnpm vitest run … && pnpm build`. Load average reached
**257.66** on a 6-core box, and `vm_stat` showed **~488 MB free of 32 GB** —
which is exactly why forks could not start. Load fell to ~20 once those runs
eased.

**Durable consequence:** the suite is not reliably runnable while a second agent
session is active on another repo on this machine, and `--maxWorkers=1` starts
workers where the config's default 4 does not.

## A real fragility found on the way

`tests/domain-lib.test.ts` gives `runCli(['--offline'])` a **5 000 ms** budget.
That CLI walks the repo (`scanned=497`) and measured **8.735 s total at 11 %
CPU** — 0.76 s user, 0.24 s sys, the rest blocked. So the test is load-sensitive
by construction and will flake on any busy machine. Its own assertion is
satisfied: run by hand the CLI returns `drift=0 unlisted=0 blockers=0`, so no
file names the domain that §4.1 does not account for. Worth filing; not this
lane's file to change.
