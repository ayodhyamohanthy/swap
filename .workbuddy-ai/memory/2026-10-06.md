## The defect, and why it mattered

`match_cards` (schema.part7.sql) is built as

    FROM public.bookings b
    JOIN public.passengers p ON p.booking_id = b.id
    JOIN public.profiles   pr ON pr.id = b.user_id        <-- INNER
    WHERE b.open_to_swap AND p.status = 'CNF' AND NOT p.is_child_no_berth;

and `get_matches()` is a bare `SELECT * FROM public.match_cards` narrowed on
train/date/class. An INNER JOIN on `profiles` means a booking whose owner has no
`profiles` row is not ranked lower or filtered later — it is **invisible** to the
only path cross-user matching has.

Part 1's own comment claimed the row is "Created on first Google sign-in".
Nothing implemented that sentence.

**A second, identical sibling found by asking whether the first had one:**
`settings` holds one row per user too, and `server/admin.ts:155` pauses an
acceptor with an UPDATE on it. A Supabase UPDATE matching no row affects 0 rows
and returns NO ERROR, so "pause this acceptor" reported success and did nothing.

Both are in one migration on purpose — a fix that ships a known-identical bug
beside it is the failure this repo documents repeatedly.

## Fix

`app/supabase/migrations/20261006010000_user_rows_on_signup.sql` — migration #4.
`handle_new_user()` on `auth.users` AFTER INSERT, `SECURITY DEFINER SET
search_path = public`, revoked from PUBLIC and granted to nobody, both inserts
`ON CONFLICT DO NOTHING`, no `RAISE` (a raise on `auth.users` turns a duplicate
into "you cannot log in"). Name derived from `raw_user_meta_data`'s
`full_name`/`name`: first whitespace token, and the FIRST LETTER of the last
token only. `gender` left NULL rather than inferred. The settings insert names
only `user_id` — every other column carries its default in the table definition,
and a default restated is a default that can drift.

**No backfill, deliberately:** both Supabase projects are uncreated (docs/12 §4),
every table holds zero rows, and a backfill could not reuse the derivation
without copying it — which migration #2's own header forbids.

**L8's live suite needed no edit.** Its `get_matches` assertion was right about
production and the schema was what was missing; a working trigger makes it pass
as written. It gained the precondition test that names this failure first
instead of letting it surface as a confusing RLS error.

Guards in `tests/schema.test.ts`: **13 mutations, 13 caught, 0 missed** —
including the two link guards that stop a LEFT JOIN from making every test pass
while re-introducing the blank-name match card rule 13 forbids.

## Session 2 (2026-10-06, ~08:50–09:15Z) — chat-guard phone parity, migration #5

Re-claimed L8 (it was released at 07:05Z). Committed `dbb5390`.

### Defect: the DB chat guard demanded ten CONSECUTIVE digits

`check_message_safety()` used `[6-9][0-9]{9}`; `lib/chat-guard.ts` uses
`[6-9]\d{4}[\s-]?\d{5}` — a separator is allowed after the 5th digit. So
`98765 43210` was flagged on the sender's device and stored
`flagged_risky = false`. The receiver's screen reads the ROW (`chat-sync.ts`),
not the text, so the warning reached nobody.

Measured against PostgreSQL 18.3 with `chat-parity-differential.mjs`, which runs
the real TS module AND the real trigger over one 35-case corpus and reports
divergence **by direction** (`TS=true/SQL=false` is a hole; `SQL=true/TS=false`
merely hides a message):

- before: **26 agree / 8 dangerous / 1 over-flag**
- after:  **31 / 3 / 1**

The 8 were TWO root causes, not eight bugs: 7 phone-shape, 1 `squishEvasion`.
The grouping is what turned a failure list into a diagnosis.

### Why the parity test did not catch it

`chat-safety-parity.test.ts` compares the guards' WORD LISTS and its own header
says it "cannot verify the regex *shapes* … and leaves shape to review". Shape
was deferred to a human reading two regexes side by side, and was never reviewed.

That header also claims **"no lookahead in Postgres"** — false. Probed with ten
paired positive/negative controls: PostgreSQL 18.3 supports lookahead AND
lookbehind, and the TS `squishEvasion` regex runs verbatim. The constraint that
justified the gap did not exist. (Positive-only probes are worthless —
"supports lookahead" and "silently always true" look identical.)

### New precedent: MODIFYING a baseline object

Migrations #2–#4 each ADDED an object, so the baseline (`schema.part*` →
`schema.sql` → `init.sql`, one schema byte-identical three ways) could stay
frozen. Migration #5 MODIFIES `check_message_safety`, which init already
defines — and `chat-safety-parity.test.ts` reads the BASELINE. A migration-only
fix would leave that test green while it read a superseded copy of the function.

So: baseline (all three mirror files) + migration, with `schema.test.ts` pinning
the two bodies byte-identical. Mirror hashes `4e8101565f84139c` → `f1e2ff6f985dccae`.

The parity test is L5's surface, so it could not be repointed at the migrations —
which is what forced the baseline edit rather than making it optional.

`nine eight 200 12345` still diverge. Both are portable (proven). Separate topic.

### New trap

**A mutation harness that RENAMES a file must delete it on restore.** Writing the
originals back left `20261005000000_chat_guard_phone_parity.sql` sitting in

### Defect still open from the previous session

**`locked_berths` is broken.** Executed: each party to a locked swap sees only
their OWN berth, so rule 13's post-payment reveal does nothing. A stranger
correctly sees nothing, so it is a dead feature, not a leak. Cause:
`security_invoker = true` reads `passengers` as the caller, part 7 drops
`passengers_match_read`, and the INNER JOIN loses the other side. Fix is a
SECURITY DEFINER reveal path that checks party membership itself, the shape of
`get_matches()`. Harness `locked-berths-test.mjs` already exists.
