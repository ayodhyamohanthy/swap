# 2026-10-06 — the profiles gate: matching returned nothing for every real user

Branch `docs/instructions-v2`. Two commits: `5ca44f3` (fix + guards), `867aca6` (docs record).

## The defect, and why it mattered

`match_cards` (schema.part7.sql) is built as

    FROM public.bookings b
    JOIN public.passengers p ON p.booking_id = b.id
    JOIN public.profiles   pr ON pr.id = b.user_id        <-- INNER
    WHERE b.open_to_swap AND p.status = 'CNF' AND NOT p.is_child_no_berth;

and `get_matches()` is a bare `SELECT * FROM public.match_cards` narrowed on
train/date/class. An INNER JOIN on `profiles` means a booking whose owner has no
`profiles` row is not ranked lower or filtered later — it is **invisible** to the
only path cross-user matching has.

Part 1's own comment claimed the row is "Created on first Google sign-in".
Nothing implemented that sentence.

**A second, identical sibling found by asking whether the first had one:**
`settings` holds one row per user too, and `server/admin.ts:155` pauses an
acceptor with an UPDATE on it. A Supabase UPDATE matching no row affects 0 rows
and returns NO ERROR, so "pause this acceptor" reported success and did nothing.

Both are in one migration on purpose — a fix that ships a known-identical bug
beside it is the failure this repo documents repeatedly.

## Fix

`app/supabase/migrations/20261006010000_user_rows_on_signup.sql` — migration #4.
`handle_new_user()` on `auth.users` AFTER INSERT, `SECURITY DEFINER SET
search_path = public`, revoked from PUBLIC and granted to nobody, both inserts
`ON CONFLICT DO NOTHING`, no `RAISE` (a raise on `auth.users` turns a duplicate
into "you cannot log in"). Name derived from `raw_user_meta_data`'s
`full_name`/`name`: first whitespace token, and the FIRST LETTER of the last
token only. `gender` left NULL rather than inferred. The settings insert names
only `user_id` — every other column carries its default in the table definition,
and a default restated is a default that can drift.

**No backfill, deliberately:** both Supabase projects are uncreated (docs/12 §4),
every table holds zero rows, and a backfill could not reuse the derivation
without copying it — which migration #2's own header forbids.

**L8's live suite needed no edit.** Its `get_matches` assertion was right about
production and the schema was what was missing; a working trigger makes it pass
as written. It gained the precondition test that names this failure first
instead of letting it surface as a confusing RLS error.

Guards in `tests/schema.test.ts`: **13 mutations, 13 caught, 0 missed** —
including the two link guards that stop a LEFT JOIN from making every test pass
while re-introducing the blank-name match card rule 13 forbids.

## Traps hit again

- **BSD `\|` is a LITERAL PIPE** — hit **three more times** today
  (a `CREATE TRIGGER` search returned nothing and I nearly reported "zero
  triggers" when there are seven; `describe(` search; `git diff | grep`).
  Always use the Grep tool or `grep -E` with a plain `|`.
- `cat -A` is GNU-only. BSD `cat` rejects it.
- **zsh does not word-split unquoted variables** — `$FILES` passed as one
  argument. Use explicit paths or `${=VAR}`.
- **`npm run collab-check` is slow (~18 min)** because it runs typecheck + the
  full suite. Use `--hook` semantics when you only want the structural checks.
- **The shared index is contended.** A surgical `git update-index --cacheinfo`
  staging was silently reverted between two of my commands (another agent
  reset/added). Fix: stage and commit in ONE bash invocation, with a guard that
  aborts unless `git diff --cached --name-only` is exactly the expected set.
  See `stage-lanes-mine-only.mjs` in the node workspace.
