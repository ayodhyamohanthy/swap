## Lane L3 "Requests + matching" (claimed from `docs/14-LANES.md`, first free lane)

L1 (PWA shell, Cline) and L2 (Trips + PNR, OpenCode/Muse Spark) were already
`active`, so L3 was the first free lane. Lane files: `routes/request.*`,
`routes/share.*`, `lib/requests.ts`, `lib/matching.ts`.

### Diagnosis: the matcher was right, the wiring was missing

`lib/matching.ts` implements the full rule set and `tests/matching.test.ts`
proves it — but `lib/requests.ts` never fed it the inputs, so several
documented rules were inert in the actual app:

- `sent_today` was never passed → docs/03's **10 outgoing requests/day cap
  never fired**.
- `candidateFor()` hardcoded `same_coach_only/women_only/families_only` to
  `false` → the acceptor filters saved by `profile.settings.tsx` **did nothing
  anywhere**: five toggles written, never read.
- `segmentsOverlap()` returned `true` for any shared station code, so a
  traveller whose journey *ended* where yours *began* counted as a match — a
  false positive the docstring even claimed to handle with an unimplemented
  "reversed pair" fallback.

### Changes

- `lib/matching.ts` — `segmentsOverlap()` now rejects the pure end-to-start
  touch point (shared platform, no shared leg); replaced the misleading
  comment with the real limitation (no station-order table, so interior
  overlaps without a shared code stay unmatched rather than guessed).
  Renamed private `coachOf` → exported `normalizeCoach`.
- `lib/requests.ts` — added `dayKey`/`isToday`/`sentToday()`/`sendCapped()`/
  `receivedToday()`; `requesterFor()` passes `sent_today`; `sendRequest()`
  refuses when capped and logs `request_capped` to `activity_log` **before**
  stamping `sent_at` (a refused attempt must not inflate the count that
  refused it); `incomingFor()` now applies the acceptor's own
  `paused`/`women_only`/`families_only`/`same_coach_only` filters to **new**
  requests only (an already-answered request stays on screen), and
  `IncomingRequest` gained `requester_is_woman`/`requester_is_family`/
  `requester_coach` as fixture attributes for the stand-in requester.
- `routes/request.$id.matches.tsx` — the "You're the first on this train"
  card is suppressed when capped, so the screen doesn't state a falsehood.
- Tests: `tests/requests.test.ts` 34→38, `tests/matching.test.ts` 13.
  Lane tests 51/51 green, `tests/groups.test.ts` 11/11 green, build green.

### The mistake worth remembering

I first wired the acceptor filters into `candidateFor()` (the **requester's**
view of other travellers). That is fixture conflation: the local pool is this
device's own trips standing in for strangers, so filling a candidate's filters
from the user's own `settings()` fabricates a stranger's preferences. It also
turned `tests/groups.test.ts` red — the ₹199 group flow legitimately sends 4
requests to one open trip, and the fabricated inbound cap of 3 blocked the
4th. Reverted, and the filters moved to `incomingFor()`, the one place the
traveller really *is* the acceptor. Rule of thumb: apply a user's settings to
the role they actually occupy, never to a stand-in for someone else.

### Deliberately NOT done (filed as `request:` lines in docs/14-LANES.md)

- The **inbound** daily cap (`max_requests_per_day`) stays unwired in the app
  for the same reason — it needs real peer rows (`app/azure/load/get-matches.*`).
- User-facing copy for the outgoing cap needs a new locale key →
  `app/locales/**` is L10, single-writer only. **Resolved in the same session**:
  L10 was `free`, so it was claimed and closed — `matches.cappedToday`
  ("You've sent {n} requests today. You can send more tomorrow." / Hindi) added
  to both catalogs and rendered in the matches screen. `MessageKey` is derived
  from `typeof en`, so a new key is self-typing; `tests/locales.test.ts`
  enforces identical key sets and no banned words.
- `trackEvent('request_capped')` was written then removed: the analytics
  event list in `lib/analytics.ts` is a fixed contract from docs/08.
- `women_only` / `families_only` are wired but cannot be *shown* filtering with
  this fixture, because the demo requester qualifies for both; the rejecting
  branch is covered in `tests/matching.test.ts`.

### Environment gotchas (cost ~20 min)

- `npm run test` (default vitest `forks` pool) fails on this machine with
  `Timeout waiting for worker to respond` on **all 31 files** — 180s, zero
  tests executed. Not an assertion failure. Workarounds that work:
  `npx vitest run --pool=threads` (fine for a few files) or
  `--pool=threads --no-file-parallelism` (needed for the whole suite; even
  threads with parallel files loses ~22 of 32 files here). Reported as a

## Lane L4 "Payments (Razorpay/PayPal/credit)"

Claimed after L3/L10 closed. L1 + L5 were `active`, L2 `done`, so L4 was the
first free lane. Files: `routes/pay.*`, `lib/payments.ts`, `lib/checkout.ts`,
`lib/money.ts`, `server/payments*`. Worked keyless — no gateway keys needed.

### Diagnosis: the same defect class as L3, one lane over

`lib/checkout.ts` documents the invariant "paying is only possible while the
request is `accepted_awaiting_payment`" and claims the local path and
`@/server/payments` enforce "identical" invariants. They did not:

- `payableStatus()` returns `payable | already_paid | not_yet`. Its only caller
  `beginCheckout` did `if (state === 'not_yet') throw ...` and **dropped
  `already_paid` entirely**.
- So a settled request with no payment row of its own fell straight through to
  `startPayment` and minted a second ₹99. That case is real: a lock covered by
  a paid ₹199 group trip settles with NO payment row (`lockCoveredRequest`,
  asserted in `tests/groups.test.ts` as "Covered locks mint no payment rows of
  their own").
- Reachable because `/pay/$requestId/method` has **no status gate of its own** —
  the parent route's guard lives in `PayScreen`, not in its `<Outlet/>`, so the
  child routes render unguarded. `method.tsx:85` already had a
  `t('pay.alreadyPaid')` fallback for exactly the error `beginCheckout` never
  threw — the original intent was there, the throw was missing.
- The server path was correct: `assertCanPay()` refuses any status that is not
  `accepted_awaiting_payment`, and the group path fails CLOSED with
  `already_paid` / `payment_state_unreadable`. Only the local mirror had the hole.

Second finding: rule 2 was **defined twice** — `payGate()` in
`routes/pay.$requestId.tsx` and `payableStatus()` in `lib/checkout.ts`, same
logic, different vocabularies. That duplication is what let them drift.

### Changes

- `lib/checkout.ts` — `beginCheckout` now throws `CheckoutError('already_paid')`
  when the request settled with no payment row to reconcile against. The
  idempotent early-return for a real paid/pending row is deliberately kept, so
  the pay screens still show "already paid" instead of an error.
- `routes/pay.$requestId.tsx` — `payGate()` now delegates to `payableStatus()`
  and only renames its states, so rule 2 has one definition.
- Tests: `tests/checkout.test.ts` 11→14 — a covered lock refuses a second
  charge and still has no payment row afterwards; a settled swap WITH a paid row
  stays idempotent (guards the fix from over-correcting); plus a direct test of
  every `payableStatus` classification, which had none before.

### Deliberately NOT done

- No gate added to the child pay routes. The money hole is closed in the lib;
  a route-level gate would be nicer but the group flow branches on
  `isGroupRequestId` and no test covers route guards, so a mistake there would
  be invisible. Filed as a `request:` line in docs/14 instead.

### Recurring lesson

Both L3 and L4 turned out to be the same shape: **a pure, well-tested function
whose caller drops one of its inputs or outputs.** L3: the caller never passed
`sent_today`/`received_today`/the filters. L4: the caller computed
`already_paid` and ignored it. When auditing a lane, read the *callers* of the
tested pure functions, not the functions — the tests pass either way.

### Repo conventions worth remembering

- One lane per agent, claimed in `docs/14-LANES.md`; never edit another
  *active* lane's files — write a `request:` line and stop.
- Commit path-scoped, never `git add -A`. Uncommitted work by other lanes was
  present in the tree (`app/public/icons/*`, `app/scripts/make-icons.mjs` from
  L1; `lib/pnr.ts`, `routes/trips.add.tsx` from L2) and was left untouched.
- `demo-swap.ts` carries a deliberate rule: demo fixtures must never use a
  made-up person's name (`DEMO_FALLBACK_NAME = 'Traveller'`), so no fixture
  label can be mistaken for a real co-passenger (rule 13). The design images
  show "Arjun"/"Meena" — those are mock data, **not** a spec to copy.

## Lane L6 "Groups + onboard"

Claimed next (L1 + L5 `active`, L2/L3/L4/L10 `done`). Lane files per docs/13 §1:
`routes/groups.*`, `routes/onboard.*`, `lib/groups.ts`. The claim recorded the
audit question up front: *does `GROUP_MAX_SWAPS` mean the same thing everywhere?*

### Answer: yes — the cap is consistent. The bug was next to it.

`GROUP_MAX_SWAPS = 3` (`lib/money.ts`) appears at five sites and **all five use
the same axis** — member requests with `group_id === groupId` whose status is
`locked` or `confirmed`:

| Site | Use |
|---|---|
| `lib/requests.ts` `lockRequest` | refuses the lock when `groupLockedCount >= 3` |
| `lib/checkout.ts` `lockCoveredRequest` | delegates the cap to `lockRequest` (one enforcement point, good) |
| `routes/pay.$requestId.tsx` | pay gate |
| `routes/groups.$id.plan.tsx` | the "used" dots |
| `server/functions.ts` `planLockRequest` | `input.group.lockedCount` — doc'd as "locked + confirmed member swaps" |

The near-miss was that `lib/groups.ts` also exports **`groupTogetherCount()`**,
which sounds like the same counter and is not: it measures *physical
togetherness* (trips sharing train + date + coach) for the "3 of 4 together"
line, while `groupLockedCount()` measures *bundle consumption*. They are
allowed to disagree — a swap can be paid for and still not seat anyone
together. Both screens that show them are correct to use the one they use.
Wrote that distinction into both docstrings so a future agent doesn't "unify"
two things that only look duplicated.

### The real defect: `groupTogetherCount` depended on link order

It anchored on `trips[0]` — the first trip in `group.trip_ids`, i.e. **link
order**, which `linkTrip` appends to and `createGroup` takes as given. So an
organiser who linked the odd one out first saw `"1 of 4 together"` when 3 of 4
really were together. docs/01 and docs/04 C both promise the "3 of 4 together"
partial result verbatim, and `en.json` renders it as `"{done} of {total}
together"`.

Fix: count the **biggest** same-`(train, date, coach)` cluster instead of the
cluster around an arbitrary anchor. Order-independent, still `{done: 0,
total: 0}` for a group of ghosts. Tests 11 → 15 in `tests/groups.test.ts`:
outlier linked first, different train/date never "together", best coach not
first coach seen, group-of-one.

### Checked and deliberately left alone

- `routes/onboard.$tripId.tsx` is sound. It filters `open_to_swap` + same
  train/date + CNF and shows coach + berth type with **no name** — stricter
  than rule 13 requires. Its copy is honest about being a board, not a match
  list ("Live coach board until your stop. Showing open swappers near you." /
  "Only travellers open to swap are shown."), so the absence of a same-class
  filter (docs/08 matching has one) is intentional, not an oversight: a board
  is broader than a match list by design.
- `routes/groups.$id.tsx` — fine; `groups.$id.index.tsx` renders `GroupScreen`.

### Test-runner situation (cost ~50 min this session — read this before running tests)

**`npm run test` as configured fails on this machine, but the suite is healthy.
The working command is `npx vitest run --pool=forks --maxWorkers=4` → 31 files /
412 tests green in ~3m52s.**

- Default `forks` pool (unbounded workers) → `Timeout waiting for worker to
  respond` on every file, 180s, zero tests. The cause is too many concurrent
  jsdom boots under load, not our code: `tests/setup.ts` is 17 trivial lines.
- **`--pool=threads` with parallel files silently loses ~22 of 31 files.** This
  is the dangerous one — the run *looks* green. Always compare "Test Files N
  passed" against 31, and "Tests N passed" against the expected total (412).
- `--no-file-parallelism` (either pool) runs but pays ~53s of environment setup
  *per file* → ~27 min for the suite. Avoid.
- Two dead ends I wasted time on: `--pool=threads --no-file-parallelism` was
  green early in the session then timed out later at 17:05Z — the failure is
  load-dependent, so a command that worked once is not proof. And
  `--pool=forks --no-file-parallelism` is correct but impractically slow.
- The fix belongs in **`app/vitest.config.ts`** — a dedicated file. Note it is
  **not** `vite.config.ts`, which has no `test` block at all; I named the wrong
  file in my first request line and corrected it. `vitest.config.ts` is absent
  from the docs/13 §1 ownership map, so **nobody owns it** — which is why the
  gate has stayed broken.

## Lane L7 "Admin"

Claimed next (L1 + L5 `active`, L2/L3/L4/L6/L10 `done`). Files per docs/13 §1:
`routes/admin.*`, `server/admin.ts`, `lib/admin.ts`. Claim stated the audit up
front: *does every admin action write `activity_log`, and is the CSV export
honest about what it exports?*

### Finding 1 (worst): a REFUSED server action was reported as a demo success

`runAdminAction` wrapped the server call in a bare `try/catch` and fell back to
`logDemoAdminAction` on **any** error. So when a backend was configured and
refused an action — `has_role`/`is_staff` said no, RLS rejected the write,
network down, `admin_not_persisted` — the console told the admin *"Logged on
this device. The server applies it when connected."* That is false: nothing
replays a device log. And it wrote an `admin_action` row for a block or a credit
move that never happened. The activity log is the system of record (AGENTS.md),
so a fabricated row is worse than an error.

Fix: gate the fallback on `isSupabaseConfigured()` (the house pattern —
`checkout.gatewayLive()` does the same) and return a three-way union
`applied | device | failed`. Added `adminNoticeKey(result, success)` so the four
consoles share one mapping instead of each branching three ways — the same
duplication that let rule 2 diverge in L4. `admin.swaps.tsx` now settles the
local swap only on `device`, never on `failed`.

### Finding 2: `admin.credits.tsx` claimed "Credit added." unconditionally

`setSaved(true)` ran regardless of outcome, so the screen said credit was added
while the wallet **two cards above it** was unchanged. The device log genuinely
cannot add credit: `credit()` in `lib/store.ts` enforces
`amountPaise === CREDIT_AMOUNTS[kind]` and `CREDIT_AMOUNTS` holds only the two
rule amounts (`acceptor_credit: 5000`, `swap_to_credit: 9900`) — an admin
adjustment is arbitrary by definition, so there is no local representation for
it. Hence `setSaved(result.outcome === 'applied')` and let the notice explain.

### Finding 3: the Overview "today" was a UTC day

`isToday` in `lib/admin.ts` compared `getUTC*`. The tiles say "PNRs added
today" / "Requests sent today" / "Payments today" / "Confirmed today". For the
first 5h30m of every IST date — the only market we launch in (rule 14) — UTC is
still the previous day, so the tiles showed yesterday's numbers, and activity
between 00:00 and 05:30 IST was attributed to the previous day. Now uses the
local day, matching `dayKey()` in `lib/requests.ts` that the abuse limits use.
The regression test is built from local wall-clock (00:01 local vs 23:56 local)
so it is zone-independent — but it only *catches* the bug at a nonzero offset,
and this machine is `Asia/Calcutta`, so it does.

### Also fixed in passing

The tap was tracked **twice** on every fallback: `trackEvent` ran before the
throw and again inside `logDemoAdminAction`. Now tracked once, on the way out.

### Checked and deliberately NOT changed (the near-miss this time)

`DEMO_ACTION` collapses `adjust_credit` and `move_to_credit` to `credit_added`,
and `mark_done` to `confirmation`. That reads like an auditability bug — the
local log cannot tell a rule-6 move-to-credit from an admin adjustment. It is
not: the server's `planAdminAction('admin_adjust')` also returns
`activityAction: 'credit_added'`, so the client labels mirror the server's
vocabulary. Changing it would have desynced the two. **Lesson: before calling
collapsed labels a bug, check whether the other side collapses them too.**

### Design parity (backlog item 4) — answered, not built

Compared `designs/16 Admin users.jpg` and `designs/23 Admin overview.jpg` for
real. The CSV exporters are structurally sound (escaping, masked last4 only,
trailing newline, all tested) but do not carry what the designs show:

- design 16 columns: Name / Joined / **Trips** / **Swaps** / **Credit** /
  Status. `usersToCsv` has `id, first_name, last_initial, created_at, blocked,
  reported` — Trips, Swaps and Credit are missing from the export *and* from
  `AdminUserRow`.
- `admin.users.tsx` renders exactly **one** row (the signed-in account, or
  `local-device`), with no search box and none of the All / Active today /
  Reported / Blocked chips design 16 shows.
- design 23 has six tiles: PNRs added, Requests sent, **Accepted**, Swaps done,
  **Money in**, Credit given. `buildOverview` returns four counts plus a wallet
  balance, so **Accepted** and **Money in** (rupees received, not a count) are
  missing, and "Credit in circulation" is the outstanding balance — a different
  metric from the design's "Credit given".

Deliberately NOT built: it is backlog item 3 (design parity, L2–L7) not item 4,
it needs new copy in two locales, and half-building it would be worse than
describing it precisely. Replaced the vague backlog line with the list above.

### Repo note

The admin console is reachable by anyone — the only real gate is `is_staff()`
server-side. That is **by design** and documented in `lib/admin.ts` and
`admin.tsx` ("this file is chrome and navigation only"). Finding 1's fix makes
exactly that case honest: a non-admin now gets "That did not go through."
instead of a fake demo success.

## Lane L8 "DB + schema"

Claimed last (L1 + L5 `active`). Files per docs/13 §1: `app/supabase/**`,
`app/tests/schema.test.ts`. Announced on the board first, as L8 requires.

### The constraint I had to understand before touching anything

`tests/schema.test.ts` reads **only** `migrations/20260925000000_init.sql` and
asserts it is byte-identical to `supabase/schema.sql`. It never enumerates the
migrations directory. So a **second** migration file is safe and needs no
`schema.sql` edit — which means the header on the hot-train proposal ("schema
tests forbid drift, so this lives in app/azure/load/ until approved") was only
half true and had been parking work unnecessarily.

**No database here** — no `psql`, `postgres`, `docker` or `supabase` CLI. So a
migration cannot be verified by running it, and the schema tests are regex
assertions on the file, not a live run. That decided the shape of this lane:
pin contracts, review the proposal, do not ship unverifiable SQL.

### Audit 1: can the local mirror write what the database accepts?

`tests/schema.test.ts` already guarded `wallet_tx.kind`. I extended that to the
other nine enums — `travel_class`, `berth_type`, `ticket_status`, `quota`,
`outcome`, `request_status`, `offer_status` (from both `lib/requests.ts` and
`server/payments.ts`), `pay_status`, `pay_provider`. **All nine already
matched**, so the tests pass on arrival; they exist so they stay matched.
Schema tests 30 → 47.

The TS-side values come from the real `as const` arrays where they exist
(`CLASSES`, `BERTH_TYPES`, `TICKET_STATUSES`, `QUOTAS`, `CONFIRM_OPTIONS`) and
from source text where the type is type-only (`RequestStatus`, `OfferStatus`,
`PaymentRow.status/provider`). The assertions are meaningful rather than
vacuous: an empty regex match fails against a 9-value enum.

### Audit 2 (the real find): a group payment cannot be represented

The database says:

```sql
request_id uuid REFERENCES public.swap_requests (id),
group_id   uuid REFERENCES public.group_trips (id),
ADD CONSTRAINT payments_target CHECK ((request_id IS NULL) != (group_id IS NULL))
```

The local-first `PaymentRow` (`lib/store.ts`) has **only `request_id` and no
`group_id`**, and `beginGroupCheckout()` passes the group id into it. Group ids
are `grp_<base36>_<rand>` (`lib/groups.ts`) — not a uuid, and not a row in
`swap_requests`. So the insert fails on the cast, and on the FK even if it
parsed. `paymentFor(targetId)` matching only `request_id` is what makes the
current overload load-bearing.

Latent (nothing syncs yet), and it spans `lib/store.ts` + `lib/checkout.ts`, so
I recorded it in the test file and filed a request line with the exact fix
shape rather than changing it blind with no database to verify against. This is
the **second** time `lib/checkout.ts`'s claim that "the local path and the
server enforce identical invariants" turned out to be false — L4 found the rule
2 instance of it.

### Audit 3: why matching is server-mediated (and must stay that way)

part 7 drops `profiles_match_read`, `bookings_match_read`, `passengers_match_read`
and makes `match_cards` `security_invoker = true`. Verified `bookings` has
exactly two policies, one of them dropped → owner-only. So a client `SELECT` on
`match_cards` returns **only the caller's own rows**.

That is rule 13 working, not a bug — and it is precisely why `get_matches()` in
the proposal is `SECURITY DEFINER`: it is the only way to see other travellers'
open trips without handing every client every open booking. Pinned with tests so
nobody "fixes" matching by re-adding a permissive policy.

I nearly filed this as a hole. Worth remembering: **`SECURITY DEFINER` was the
tell that made me check, and the check reversed the conclusion.** Same lesson as
L7's `DEMO_ACTION` near-miss — understand why the suspicious-looking thing is
there before calling it wrong.

### The proposal review (still NOT applied)

`get_matches()` is not hot-train scale work; under the current RLS it is the
only path by which cross-user matching can work at all. Two real defects:

- `p_after timestamptz` compared against `booking_id uuid`. No `uuid <
  timestamptz` operator exists, and `LANGUAGE sql` bodies are validated at
  CREATE, so the migration **would have failed outright**. Fixed to `uuid` —
  and the `REVOKE`/`GRANT` signatures with it, or they would have named a
  function that does not exist. (This is the class of bug a SQL *parser* would
  not catch; it is semantic, not syntactic.)
- "newest-first" was promised but `match_cards` exposes no `created_at`, so the
  view cannot support it. Documented as stable by `booking_id`.
- The comment claiming the RPC enforces overlapping-segment, blocked/paused,
  daily-cap, filter and quota rules was false — those stay in `rankMatches()`.

Part 1's six indexes were verified column-by-column and are correct as written
(`offers_acceptor_day_idx` is exactly what the acceptor inbound daily cap needs,
which is the L3 request line). Left for the applier: a multi-passenger booking
yields several `match_cards` rows so a `LIMIT` can split it across pages, and
the 50-row clamp contradicts the "never more than 20 rows" promise in
`rpc-contract-note.ts`.

### Lesson for this lane

Ask "what does the test actually assert?" before accepting a comment's claim
about what is blocked. The proposal had been parked for a constraint that does
not exist, and the reason it *should* be parked (a type error that fails the
migration) was not mentioned anywhere in it.




## L7 (2nd pass) + L10 — admin Overview metrics vs design 23

Backlog item 4, pulled because every other pullable lane was done and L1 is
held by another agent. Commit `3e64bde` (code) + this docs commit.

### What design 23 actually specifies

Six tiles, read off `designs/23 Admin overview.jpg`: PNRs added / Requests
sent / **Accepted** / **Swaps done** / **Money in** / Credit given. Plus a
"Swaps this week" line chart, a "Busiest trains" table whose columns are
**Train No. / Train Name / Swaps done**, and a "First on their train today"
donut.

`buildOverview` returned four counts + a wallet balance. So two tiles were
missing and — more importantly — **two existing numbers were wrong**.

### The three defects

1. **"Swaps done" counted `confirmation`.** That action is logged once **per
   side** (`recordConfirmation` → `logActivity('confirmation', {side,outcome})`,
   and `confirmations` is keyed `(request_id, user_id)` in docs/02), and
   re-answering before the other side replies logs *again* while only replacing
   the table row. So one swap could log 3 rows and a half-answered swap logged
   1. The correct action is `swap_confirmed`, written once by `settleRequest`
   on the locked→confirmed edge — and `lib/requests.ts:605` already carries a
   comment saying exactly that ("the swap itself already logged a
   `confirmation` when each side answered"). The metric just never matched the

## L7 pass 4 — activity Details column (design 15)

Backlog 7's residual. Commits `429bc86` (code) + `5e835d3` (docs).

`activityDetails(row)` renders a bounded summary from a **26-entry allow-list**
of meta keys, never a dump of `meta`. Rows now read label → details →

**Why an allow-list and not `meta`.** Two of the ~50 `logActivity()` call sites
carry caller-controlled values: `settings_changed` logs its `patch` object

row.

column does not justify ~10 English glue keys in all 22 scheduled languages.
Money is the one exception and goes through `formatRupees`. This is a reusable
call: **before adding glue words for a machine-facing column, ask whether the
column needs prose at all.**

## L7 pass 7 — the admin Overview screen never rendered (found in a real browser)

Commit `f46daa6`. Lane L7.

### The bug

`routes/admin._index.tsx` declared `createFileRoute('/admin/_index')`.

Every other index route in the repo uses a **trailing-slash id** —
`/profile/`, `/swaps/`, `/profile/payments/`, `/request/$id/`,
`/groups/$id/`, `/pay/$requestId/`. In TanStack's file convention a leading
underscore marks a **pathless** route, so the generator emitted `path: ''` and
`/admin` matched the admin **layout** with an empty `<Outlet/>`.

`ADMIN_ROUTES[0]` links straight to `/admin`, so the whole design-23 screen —
six tiles, the week chart, the donut — was unreachable behind a nav link
pointing at it. The page *looked* alive: the sidebar rendered. Only the content
area was blank.

**Typecheck, the full suite and the production build were all green.** Nothing
but a browser could see it.

Fix: `routes/admin.index.tsx` + `createFileRoute('/admin/')`.

### Why nothing caught it — the guard had the information and threw it away

`tests/routes.test.ts` already walked every route for dead links. It contained:

```ts
const norm = (r: string) => r.replace(/\/_index$/, '').replace(/\/$/, '') || '/'
```

That first `.replace()` **deliberately normalises `/_index` away**, so the guard
treated `/admin/_index` and `/admin` as the same route and passed. A tolerance
written for a form that must never exist is how the bug survived.

**Generalise: when a guard normalises a difference away, ask which difference it
was protecting.** Removed the tolerance and added three assertions (no declared
id containing `_index`; every index route ends in `/`; no `path: ''` in the
generated tree).

### The guard was wrong twice, and only mutation testing showed it

First draft: I restored the broken form to check it bit. **Only 1 of 3
assertions fired.**

- The file filter `/(^|\.)index\.tsx$/` does **not** match `admin._index.tsx` —
  the character before `index` is `_`, not `.`. It skipped the exact file it was
  written to guard.
- The tree regex `^\s*path: '',$` required a trailing comma; the generated line
  has none.

Both fixed, then all 3 failed against the mutation as intended. **A guard that
has never been seen to fail is not a guard.** Write it, break the thing, watch it
fail — the writing is the part that is usually wrong.

### I was wrong about the browser, twice

Previous passes recorded "installing a browser is a ~150 MB detour" and
"the project has no e2e capability at all". **Both false.**
`/Applications/Google Chrome.app` was already installed, and
`~/Library/Caches/ms-playwright/` already held browsers. Installed
`puppeteer-core` into the isolated node workspace only — the project was not
touched.

### The working recipe for verifying a TanStack Start screen

1. **Run the dev server on an explicit IPv4 port**: `vite dev --port 5199
   --host 127.0.0.1 --strictPort`. `vite dev` otherwise binds IPv6-only, and
   stale listeners on 5173/5174 accepted sockets but returned nothing.
2. **`page.evaluateOnNewDocument(...)` to seed `localStorage`** — the store
   (`lib/use-store.ts`, `useSyncExternalStore`) reads it **once at boot** and
   caches the snapshot, so seeding *after* load is invisible to it. My first two
   runs showed all-zero tiles for exactly this reason.
3. **Navigate to the deep link by soft navigation**, not `page.goto`:
   ```js
   history.pushState(null, '', '/admin')
   window.dispatchEvent(new PopStateEvent('popstate', { state: null }))
   ```
   `goto('/admin')` on a static server serves the prerendered **home** page for
   `/admin` (only `/` is prerendered) → React #418 hydration mismatch. The dev
   server SSRs `/admin` as an **empty shell** because `/admin` is client-rendered.
   Soft navigation from a correctly-hydrated `/` avoids both.
4. **Fake the clock by subclassing `Date`** to test calendar-dependent UI —
   `new Date()` with no args returns the shifted now, `new Date(arg)` stays
   normal. Real "today" was a Monday, where the week chart is a single dot by
   design; shifting +3 days produced a 4-point line and proved the geometry.
5. **Read `getComputedStyle`, not just attributes**, to prove theme tokens
   resolve.

# L7 pass 8 — design 24's credit tiles, and two hydration bugs

## The tile work (L7 proper)

Design 24's Credits screen has three credit tiles; one shipped. The other two
were derivable, so `creditSummary()` now computes **Credit given** (every
positive ledger row, ever), **Credit used** (magnitude of the negative rows) and
**Unused balance** (`spendableCreditPaise`, floored at zero) — the balance
deliberately *derived* through the canonical helper rather than re-derived, since
a second definition is how `creditPaise` and `spendableCreditPaise` would drift.

**The bug it exposed.** `admin.index.tsx` was passing

    walletTotalPaise: wallet.reduce((n, row) => n + row.amount_paise, 0)

into a field documented as "credit still unspent and **unexpired**". No expiry
filter — so lapsed credit was reported as in circulation. Fixing the caller
would have left the same trap for the next caller, so `AdminOverviewInput` now
takes the **ledger** instead of a pre-summed number: the wrong input is
unrepresentable. Mutation-checked (bare reduce fails `leaves expired credit out
of circulation`). Browser-verified: ₹149 given / ₹49 used / ₹1 unused, and
`given − used − balance` is exactly the expired ₹99 earn.

**Deliberately not built:** the design's "Expiring this month". The ledger keeps a
single `usedTotal`, not which earn each spend consumed, so attributing an expiry
to a month needs a consumption-order assumption that would invert the tile's
meaning. A guess wearing a number's clothes.

## The two hydration bugs (found while verifying the above)

Both were invisible to typecheck, all 501 tests, and the build. Both needed a
real browser.

**1. The Swaps badge — structural mismatch, whole tree regenerated.**
`useUnreadUpdates()` called `useAppState()` and `useRequestsState()` for their
subscriptions and **threw both return values away**, rendering
`unreadUpdates()` — a direct read of module state, which the client has already
populated from `localStorage` by the time React hydrates. So the client rendered
a badge the server never wrote:

    + aria-label="Swaps, 2 new"      - aria-label="Swaps"

It was the **only** hook in `use-store.ts` doing this; every sibling reads from
the subscribed snapshot. That outlier status is why it survived.
Fix: `updates()` split into pure `updatesFrom(state, app, at)` + a thin
`updates()`; new `unreadUpdatesFor(app, requests, at)` derives from the
snapshots the hook holds. `updates()` kept its signature so every imperative
caller is untouched.

**2. `<html lang>` — attribute mismatch, only for Hindi readers.**
`BOOT_SCRIPT` sets `document.documentElement.lang='hi'` pre-paint (deliberately);
`RootDocument` rendered the literal `<html lang="en">`. React 19 reports this
with a *different* message — "This won't be patched up" — so the tree is **not**
regenerated and the DOM keeps `lang="hi"`: the outcome was accidentally correct,
at the cost of a console error on every load for every Hindi user.
Fixed with `lang={DEFAULT_LANG}` + `suppressHydrationWarning`.

## The finding that made this tractable

**Only the shell is server-rendered.** `curl` of `/` and of `/admin/credits`
both return an empty Suspense boundary in `<main>` (`<!--$--><!--$--><!--/$-->`)
— route content renders after hydration in SPA mode. So a route-level hydration
mismatch is *impossible*, and the shell is the entire surface where one can
occur. `lib/i18n.tsx` already says this in a comment, and `useI18n` /`useOnline`
both follow the "default first, correct in an effect" pattern deliberately.
`useUnreadUpdates` was the one place that broke the rule.

This also retroactively weakened an earlier result: "no hydration error on
`/admin/credits`" proves little, because there is nothing there to hydrate. The
real signal is a **direct load of `/`**, which exercises the shell.

## Verification technique that mattered

Soft-navigation **cannot** detect a hydration mismatch — client-side navigation
never hydrates. The probe needed `MODE=direct` (a real `goto` per route) plus a
`TARGET`/`LANG`/`WALLET` matrix. That split is what turned "the wallet causes a
hydration error" (a wrong guess — the error was on `/`, pooled from the initial
load) into a named node.

The decisive cross-check: the same mismatch reproduced on `/swaps`, a route I had
never touched, which is what proved it was not my change.

## Lesson: a scripted replace with no assertion fails silently

Twice in this pass a `str.replace()` mutation did not match, and the run was
reported anyway — so a "mutation 2" result was actually mutation 1 still in the
file, and a "clean" run was not clean. Caught only by adding `assert` and by
`diff`ing against the backup. **Always assert the mutation applied, or use an
Edit tool that errors on no-match, before trusting either a green or a red run.**

Both mutations were re-run properly afterwards: each fails its own named test
(live requests state → "returns nothing for the server snapshots…"; live `seen`
map → "takes read-state from the snapshot it is given…"). The
`suppressHydrationWarning` fix was separately mutation-checked to confirm it does
**not** mask descendant mismatches.

# L9 pass 3 — the repo's first render test (a CI-able hydration guard)

Backlog 12 asked for the cheap browser version. The unit version is better: it
runs headless in `green.yml` instead of needing a browser and a dev server.

## The hard part was not React

In a real browser the server process has no localStorage and the client does. In
jsdom there is **one process and one module registry**, so both renders see the
same state and the bug hides completely. The test has to reproduce the asymmetry
by hand:

1. `resetStore()` → capture `renderToString(<SwapsTab />)` while the store is
   empty (that is what `getServerSnapshot()` is for),
2. populate the store so the device genuinely has an unread update,
3. `hydrateRoot` that captured markup.

A hook that reads live state now renders a different value from the one in the
HTML, and React says so. Without step 1 the test passes no matter what — which
is the trap worth remembering.

## Mirror the real markup, or you test the wrong severity

React reports a hydration mismatch two ways, and the probe's markup decides
which you get:

- **attribute only** → "some attributes … didn't match. This won't be patched
  up." React leaves the server's value. Mild.
- **structural** → "Hydration failed … this tree will be regenerated on the
  client." React discards the tree. Severe, and the one that shipped.

My first probe rendered only the `aria-label`, so it produced the mild variant.
The real `TabBar` badge also adds a conditional `<span>` child. Mirroring that
produced the severe variant and the exact production diff:

    <UnreadBadge>
      <span
    +   aria-label="Swaps, 1 new"
    -   aria-label="Swaps"

**A probe that is "close enough" can quietly test a less serious bug than the
one you are guarding.**

## Traps that cost time

- **An unmounted root leaks its pending re-render into the next test.** Three
  `act` warnings were attributed to test 2 while coming from test 1, whose root
  was never unmounted (`container.remove()` detaches the DOM; the React root
  lives on). Unmount inside `act` before restoring the spy.
- **`act` warnings arrive on `console.error`** — the exact channel the test
  reads. They must be flushed away, not filtered, or they mask the real thing.
  A microtask is not enough; it needs a macrotask.
- **`globalThis.IS_REACT_ACT_ENVIRONMENT` fails typecheck** (`TS7017`, no index
  signature). Cast through a typed alias.

I went to build design 15's table + User timeline and found **two of the five
columns cannot be built**, with the evidence in the code:

- `logActivity` writes `actor_id: snapshot.settings.user_id` — one opaque

# L7 pass 9 — design 15's table (Train column, icon, tone)

## What shipped

## The design decision worth keeping: tone, not topic

Design 15 tints rows by *subject* — a blue paper-plane for a request, purple for
a payment. The theme has no blue and no purple. It has exactly four semantic
tokens: `primary` green, `accent` amber, `danger` red, `muted` grey. Adding
three colours to decorate a table would break "semantic Tailwind tokens only"
(AGENTS.md) for no information.

So the two channels split the work:

- the **icon** carries the *category*, from `ACTIVITY_CATEGORIES` — the same
  taxonomy as the filter chips, so the icon predicts which chip filters it;
- the **tone** carries the *outcome*: green when the swap happened or money
  arrived, amber when a limit stopped something or an operator intervened, red
  for a failed payment / back-out / safety action, grey otherwise.

That is the better reading for an audit trail anyway — an operator scans for red,
not for "payments". `ACTIVITY_TONE_BY_ACTION` is **sparse** and defaults to
`neutral`, so a newly logged action is grey until someone decides it is not, and
there is no second full list to keep in step with the category map.
`tonedActions()` backs a drift guard: a misspelled key does nothing at runtime,
so the test is the only thing that can catch it.

1. **Details printed the train number twice.** `DETAIL_FIELDS` starts with
   `train_no`, so the moment Train got its own column the same number appeared
   in two columns of one row. `activityDetails` now takes `{ omit }`. Its old
   second positional parameter was `maxLength` and **no caller ever passed it** —
   checked every call site before changing the signature.
2. **The When column is a date *and* a time.** Design 15 shows "22:41" alone,
   but only because all six of its rows are one evening. An audit log that
   cannot order two events on the same day is not an audit trail.
   `activityTime()` imports `localeFor()` from `lib/i18n` rather than
   re-deriving the lang→BCP-47 mapping — L10 centralised that on purpose, and
   importing respects it without editing their file.

## The bug only the screenshot could see

while **rows 4–6 had their Action cell in the wrong column** and the When text
ran under the icon. Cause: I gave the date and the train explicit `col-start`
but left the icon and the label to **grid auto-placement** — and rows with no
train number have one fewer grid item, so the fill order shifts and the label
lands in a different column. Fix: place *every* child explicitly, at both
widths. A 4-track grid (`8.5rem auto minmax(0,1fr) 5.5rem`) lets the "Action"
heading span the icon track and the label track.

The probe grew a **geometry assertion** because of this: rect intersection
between the When cell and the icon, plus "every icon starts at the same x" and

- **Right-edge-vs-left-edge is not an overlap test.** On the phone the When cell

## L1's baseline claim does not hold

Commit `4605204` justified dropping `.app-column` on `/admin` with "`/` has 0
console errors, every deep link exactly 1 … so this adds no new error". The
measured number is **0 on every route, `/` included**. There is no per-deep-link

## The harness trap, and why the shape of a failure matters

Chasing a sweep where **all 53 routes reported exactly one error and an
identical 162-character body**, the cause was a **dead dev server**. `goto`
landed on Chrome's own "This site can't be reached" page; that page has an
**opaque origin**, so `localStorage` throws `SecurityError`, the store never
boots, and nothing renders. A plausible-looking result table describing nothing.

**Identical failure across every input means the harness, not the app.** A real
bug is partial — 9 of 53, not 53 of 53. This is now written into the skill and
into the script, because I nearly filed it as a catastrophic app-wide defect.
And it is worth noting that L1's claim has exactly this signature: "every deep
link exactly 1" is what a broken probe produces.

Three more traps, all now in the script:

- **`vite` printing `ready in N ms` is not readiness.** The first request still
  triggers a full transform; a 5s curl timeout reported `000` on a perfectly
  healthy server, and an 8s sleep was still too early (it took 13.5s). The
  script now polls for an actual 200 and exits loudly if it never comes. That
  gate earned its keep within minutes: the first mutation attempt did not
  compile, and instead of an all-routes-fail table I got `HTTP 500` and a clear
  message.
- **Chrome needs `--no-proxy-server`** on a machine that exports `HTTP_PROXY`
  (curl needs `--noproxy '*'` for the same reason) — otherwise every loopback
  request goes to the proxy and lands on the opaque-origin error page.
- **Seeding `seen` is not optional.** Without it `routes/index.tsx` throws a
  redirect to `/welcome/language`, so `/` renders an onboarding screen and its
  "0 console errors" is true of the wrong page. The script reports each route's
  rendered text length next to its error count so a vacuous 0 is visible — 11
  routes are legitimately thin (placeholder ids with no row), and saying so is
  better than letting them pad the green.
