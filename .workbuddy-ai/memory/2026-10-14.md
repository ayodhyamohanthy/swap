## Backlog 17 — the normalisers were wired to the ENGLISH list only

**What was wrong.** Migration #7 gave the DB guard `v_squished` and `v_digits`, but
wired them to `CASH_WORDS` only. `HINGLISH_WORDS` and `HINDI_WORDS` were matched
against raw text — and `lib/chat-guard.ts:105-110` mirrored that asymmetry exactly.
So `b h e j`, `p a i s e`, `p@ise` and `b-h-e-j` were called clean on the sender's
device **and** stored `flagged_risky = false`. `chat-sync.ts` trusts the ROW, so the
receiver's screen never warned.

**The fix** is one clause per copy: `HINGLISH_WORDS.test(squished)` in
`lib/chat-guard.ts`, and `OR v_squished ~* '\y(khareed|…)\y'` in
`check_message_safety()`. All four SQL copies regenerated so the mirror stays
byte-exact. Widening is safe because `v_squished` is a superset of the raw text for
these words — it can only create a match, never remove one — and three corpus cases
(`Meet me near the b h board`, `I will be there`, `phone me later`) pin that it
manufactures none.

## Finding 1 — the instrument was the blocker, not the guard

The differential harness compares the two guards **against each other**. A message
both of them miss therefore scores as `agree`. Nine cases were agreeing on the wrong
answer while the instrument reported perfect health. **Agreement is not correctness**,
and this is the one tool in the repo built to find divergence in exactly this area.

Fixed in the instrument: a corpus entry may now carry `true` (should flag) or `known`
(should flag; recorded, bounded gap), and the verdict has a SHARED-BLINDNESS line that
no amount of agreement can hide. Measured, 63-case corpus, real TS module vs the real
trigger under PostgreSQL 18.3:

    before   9 shared-blind, 0 dangerous, 0 over-flag
    after    0 shared-blind, 0 dangerous, 0 over-flag

**A corpus entry that passes for the wrong reason is worse than no entry.** The first
draft of the group read `p a i s e bhej do`, which WAS flagged — by the raw `bhej`, not
by the evasion. It measured nothing. Rewritten to pure cases (`p a i s e de do`).

## Finding 2 — a guard hole found by mutation, not by reading

`drop-one-word-from-the-hinglish-vocabulary` **SURVIVED**: deleting `bhej` from the
real SQL alternation left every vocabulary test green.

**Why:** `triggerHas` substring-matches the guard body, and that body's own comment
contains `so 'bhej do paise' … passed`. The test was satisfied by **prose describing
the bug it exists to catch.**

This is the *same vacuity* `chat-safety-parity.test.ts`'s header already warns about —
a first version searched all of `schema.sql` and passed on a comment — fixed at the
FILE level and surviving one level down, **inside** the function body. `TRIGGER` is now
comment-stripped via the existing `scripts/staging-lib.stripSqlComments`, and
`Meetmenear` (a token that exists only in the sentinel paragraph) is the probe that
asserts prose is not searchable.

**Generalizable:** slicing to "the right region" is not the same as slicing to "the
executable part", and a region that contains prose will answer prose questions.

## Finding 3 — my own harness was lying to me

The first re-run still reported the vocabulary mutation as SURVIVED. It was not a
guard hole: `swap()` always read from `original`, so a two-step mutation wrote only its
second half and **discarded the first**. Only the squished line lost `bhej`; the raw
line kept it, and the test was right to still find the word.

**A harness bug reads exactly like a guard hole.** A survived mutation has to be
checked against what it actually did, not what it claimed. `swap()` now reads the
current file so successive swaps compose.

## Deliberately NOT fixed: spaced Devanagari

`v_squished` collapses ASCII letters only (`[A-Za-z]` lookbehind/lookahead) in BOTH
copies, so it cannot reach `प ै स े` even if asked. The HINDI list therefore stays
raw-only — a bounded decision, not an oversight:

- a Hindi speaker evading writes **Latin transliteration**, which HINGLISH now covers;
- `प ै स े` orphans the matras, and nobody types that;
- widening the class to `[[:alpha:]]` would make the SQL and JS squishers differ by
  **LOCALE** — trading a theoretical gap for a real divergence, which is the exact
  defect class #7 and #8 exist to remove.

The harness carries `प ै स े दे दो` marked `known`, so the gap is reported on every run
instead of living in a comment nobody reads.

## Filed, not fixed — the berth reveal is still unreachable

L3's `d418af0` closed my 2026-10-09 request, and the work is good: `fetchLockedBerths`
/ `mergeServerBerths` / `revealedBerthsAsync` fail closed on ambiguity, never widen the
local lock gate, and leave the keyless path byte-identical.

**But the fix re-created the defect it was filed to remove, one layer up.**
`revealedBerthsAsync` has **zero callers** — all five screens still call the synchronous
local-only `revealedBerths(id)`. And it is not merely uncalled, it is **unreachable by
construction**: it takes a `serverRequestId`, and that name appears **nowhere in
`app/src` outside `requests.ts` itself**. Local requests are minted by `newId('req')`
and no store type carries a server uuid. L3's own header says so honestly ("step-3 sync
does not exist").

**So the remaining work is not a bridge, it is step-3 sync.** Nothing writes
`swap_requests` / `swap_offers` server-side, so the uuid does not exist to pass. Until
that lands, migration #6's fix is correct and unreachable, and rule 13's reveal still
runs entirely off device state.

This is the **third** instance of "a correct server path with no reachable caller"
(`get_matches()` 2026-10-04, `locked_berths` 2026-10-09, `revealedBerthsAsync` today),
so the class is filed as backlog 18. The honest split: the cheap half (a dead export)
is grep-shaped and worth a guard; the expensive half (a caller that *cannot* exist yet)
is not, and its durable convention is to name the missing dependency in the code that
waits on it — which L3's header already does well.
