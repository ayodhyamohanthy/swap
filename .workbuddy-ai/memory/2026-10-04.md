## The harness bug, and the false 22 failures

First e2e run reported `22 failed / 62 passed`, all one viewport, all
`ERR_CONNECTION_REFUSED`, first server line `ENOENT … lock-D2Zi4xow.js` — **a
file that exists on disk.**

Root cause, proven: `serve-dist.mjs:93` was a bare `readFileSync` after an
`existsSync` check. An unguarded throw in a request handler **kills the Node
process**, so one bad request became 22 reported *product* failures.

The trigger was mine and is a real trap: `mv app/dist /tmp/...` is **required**
before a rebuild (Vite `emptyOutDir` hits `SAFE_DELETE_BULK_CONFIRM_REQUIRED`
above 50 files), but the build is **deterministic** — same source, same
filenames — so the sandbox's delete-tracking still held those paths as trashed
and refused to read the recreated files. Proved by diffing the directories: the
trashed copy and the new build share `lock-D2Zi4xow.js`, `admin-Bf5wgpkc.js`, …
name for name.

Fixed read-then-head with `try/catch` → 404. Re-ran `npx playwright test`
**without rebuilding** (dist was valid) → **84 passed, exit 0, zero crashes.**

**`app/scripts/**` is in no lane's map and no test covers `serve-dist.mjs`** —
the crash was visible only because the suite was run by hand.

### 3. The big one — the axe suite RACED HYDRATION and FAILED GREEN

Went after backlog 13 and it contradicted itself immediately:
`groups.index.tsx:44` renders an **unconditional** `<h1>`, yet axe said the
screen had none.

Measured instead of reasoned — instrumented the spec to count h1 before/after
`analyze()`:

**`h1 0 -> 1 across analyze()` on 18 of 24 screens.** The flagged set differed
run to run.

**Cause:** only `/` is prerendered and its `<main>` is **EMPTY** (React suspense
markers + an inline scroll `<script>` — `support.ts` already documents this for
a different purpose). So `goto()` + immediate `analyze()` scanned a document
with **no screen in it**.

**Why it survived: a race fails GREEN.** An empty shell reports *fewer*
violations, so "zero serious/critical" was true of a page that had not rendered.
`passes.length > 5` didn't catch it either — an empty shell passes >5 rules.

**Fix:** wait for `main > *:not(script)` (`:not(script)` because the inline
scroll script IS a child of `main`, so a bare child count is already non-zero),
**plus a stability assertion** — h1 count must not change across `analyze()`.

**Mutation-checked both ways:** with the wait, 24/24 pass; with the wait
replaced by a no-op, the assertion fails on six screens by name.

**Result: flagged set 22 → 5. 17 of 22 instances were artifacts.** Zero
serious/critical before AND after — so the race hid nothing on the contract
axis. Worth stating precisely rather than dramatising.

### Two tool traps re-confirmed

- **`grep "\|"` in BSD BRE bit me a THIRD time.** `grep -n "dist\|ROOT\|client" file`
  returned empty and I nearly concluded the file had no such lines. `\|` is a
  literal in BRE. Use the Grep tool (ripgrep) or `grep -E`.
- **The bulk-delete guard refuses ATOMICALLY.** `vite build` aborted with
  `SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":109,"threshold":50}` at
  `prepare-out-dir`, *before* deleting anything — `dist` was left byte-identical
  (same 6041-byte `index.html`, same mtime). So the earlier belief that it
  "partially deletes and mangles dist" was wrong; `mv dist /tmp/stale-dist-$(date +%s)`
  then rebuild is a clean workaround.
- **Last session's `ENOENT` was NOT a sandbox trash-keying quirk.** It was a
  *stale `serve-dist` process still pointing at a `dist` I had just moved away*,
  which then died on the unguarded `readFileSync`. Re-tested today with no stale
  server: all 77 rebuilt assets read fine. `playwright.config.ts` has
  `reuseExistingServer: !CI`, so a leftover server silently serves the old build.
